# hearth · decisions

Every design decision with its recommendation, reason, date and status. Q ids were open questions, decided the same day as the D rows; D10 and D11 were never assigned. Ids are permanent and never reused; a new row takes the next free D id. Status is decided, open (a question for the owner) or superseded by another id. This file is the only place a decision is recorded; other documents describe the result.

| D15 | How stable is `agentcore`'s API, and when does it earn v1? | v0 until shhh and hearth both ship a milestone on one tag without needing a change; then v1 with Go's compatibility promise | At v0 both consumers are the same person and the API is still shhh-shaped; freezing it before hearth consumes it would lock in shhh's assumptions. The contract is machine-checked rather than promised: agentcore's gate reports the exported-API diff against the previous tag and every tag message names its incompatible changes or says it has none; `doc.go` lists the seams, the module never learns which app calls it, and a new seam needs a second consumer that wants it. agentcore's exported API carries llm types, so an incompatible llm change bumps agentcore in lockstep, and all three repositories sit on one llm tag (v0.7.0 when this was decided). The `agent` splits (D14) wait until hearth imports the package, so the second consumer decides the cut. | as recommended | 2026-10-19 | decided |
| D16 | Socket transport: Unix socket vs loopback TCP with a token | Unix socket via Network.framework/NIO, else loopback TCP with a per-launch token, Ollama-style | connect-swift's two HTTP clients both dial a host and port: the URLSession one because Foundation has no Unix-socket API, the NIO one because its bootstrap takes host and port only and would bring swift-nio, HTTP/2 and SSL into the app for nothing. A socket would mean writing and owning a third HTTP client over Network.framework, more than a day. The token is checked on every request by middleware ahead of the router, so the peer-uid check is replaced, not weakened. Two consequences: the URLSession client has no bidirectional streaming, so the core calls native tools through a second server in the app, not a bidi stream; and the helper learns the app is gone from its stdin pipe closing, because HTTP connections are per request. | loopback TCP on 127.0.0.1, ephemeral port, per-launch bearer token; helper exits on stdin EOF | 2026-10-19 | decided |
| D17 | connect-go v1 or v2 for the first contract | v1.21.1 now; migrate with `connect-go-v2-migrate` in its own change | v2.0.0 shipped on 2026-10-07, a week before this work; its generated code and transport layer are new, the v1 line is still maintained, and the BSR has no v1.21.1 plugin yet (v1.21.0 generates code that v1.21.1 runs). The migration tool makes the move mechanical once v2 has settled. | as recommended | 2026-10-19 | decided |
